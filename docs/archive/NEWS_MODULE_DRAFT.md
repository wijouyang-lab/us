## 1. 目标

在现有 Dashboard 增加一个**金融新闻板块**，让用户打开看板时能快速看到与持仓/候选/宏观相关的最新新闻，而不必去读邮件或逐个 ticker 查。

> 明确范围：**只做"展示/聚合新闻"，不做"新闻驱动交易决策"**。新闻→信号的闭环属于 Phase 5/7 激活前的更高阶能力，本草案不涉及。

## 3. 技术约束（只评估，不实施）

### 3.1 免费源是否够用
- **Yahoo `Ticker.news`**：scan.py 已在用（`scan.py:322-387`），零额外成本、无需 Key，**但偏"个股级"、覆盖与排序质量一般**，且依赖 Yahoo 可用性（此前有 `try/except` 兜底）。适合"与持仓联动"的子场景，**不适合做市场级广覆盖流**。
- **Google News RSS**：scan.py 已用（`scan.py:1363` 等），免费、覆盖广，但**受 Google 反爬/限流影响**，需容错。
- **NewsAPI / Finnhub**：免费档有**严格日配额**（如 NewsAPI 免费 100 请求/天、Finnhub 60/分），若跟 dashboard-data 每 15 分钟跑，需精算配额是否够；否则必须降低频率或付费。
- **结论**：免费源对"个股联动 + 低频市场流"够用；对"高频 + 广覆盖市场流"不够，需付费或节流。

### 3.2 API 限流影响
- 若并入 `dashboard-data.yml`（每 15 分钟、工作日全天），免费新闻 API 配额极易耗尽 → **建议新闻独立低频，或仅在非高峰窗口拉取**。
- 限流失败必须有降级（silent fallback 到上次成功结果 / 显示"新闻暂不可用"），**绝不因新闻拉取失败阻断 dashboard 生成**（dashboard_export.py 现有 `try/except` 风格应沿用）。

### 3.3 是否增加 dashboard-data 时长
- 现状 `dashboard-data.yml` 每个 15 分钟窗口跑 `dashboard_export.py` 刷新 `dashboard_data.json`，时长敏感。
- **若新闻并入现有 workflow**：会增加单次运行时长（多一次网络抓取 + 解析），可能拖慢看板刷新；需压测。
- **建议**：新闻独立 workflow 或独立 job，避免耦合主刷新链路；或把新闻缓存为中间 JSON，主刷新只读取。

### 3.4 与现有新闻能力的复用（避免重复造轮子）
代码里**已有**新闻能力，草案应优先复用而非新建：
- scan.py 每次 Scan 已抓**个股新闻**（`yf.Ticker(ticker).news` + Google News），并写入 snapshot 的 `News_AsOf_ET` 字段（`scan.py:3059-3061, 3865`）。
- AI 已生成每只推荐股的 `news_cn`（中文新闻核查）并落 `ai_snapshot.csv`（`scan.py:3420, 3492`）。
- `dashboard_export.py:84,1205-1219` 已读取并展示 `Premarket_*` / pending 的新闻相关字段。
- **含义**："与 core/observation 联动的新闻"几乎可直接从 `ai_snapshot.csv` / pending CSV 复用，无需新数据源；只有"市场级广覆盖新闻流"才需要新增源（Q1）。
