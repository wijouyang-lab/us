## 分支 B：判决 = SYSTEMATIC（Technical_Date = 2026-10-06，即 T-2）

### 含义
- **系统性滞后 1 个交易日**，根因指向端点数据新鲜度差异（步骤 49 早于 54 的设计性错位）。
- 不是偶发，需改进告警设计以贴合"连续滞后"语义。

### 下一步（核心原则：**先改契约告警设计，不改数据源**）
1. **改契约告警设计**，不碰 `Technical_Date` 的取值、不碰 price history 数据源、不动 Gate、不动 workflow/schedule。
2. **告警改进候选（2–3 种，标代价）**：
   | 候选 | 做法 | 代价 | 备注 |
   |---|---|---|---|
   | 连续 N 天才告警 | 需跨 run 持久化计数器（文件/JSONL），触发从"每次"改为"连续 N 次" | 低–中（新增状态存储 + 路径/清理） | 防刷屏，最直接对应 SYSTEMATIC |
   | 独立 JSONL 留痕 | 每次观测追加一行审计记录，不再即时打印告警 | 低–中（需路径 + 轮换策略） | 审计友好，与计数器可叠加 |
   | 加 run_id 关联 | 告警/记录绑定当次 Scan 的 run_id | 低 | 可追溯，宜与 JSONL 搭配 |
3. **改完跑测试通过后再考虑 push**（仍走 rebase → push 流程；可单独立一个"告警改进"commit 序列）。
4. **数据源改动仍不做**，列入 backlog，等 Phase 5 激活前再评估（届时统一决定端点顺序是否要调整）。

### 风险与回滚
- 风险：改进引入新 bug（计数器状态错乱 / JSONL 竞态）→ 用现有 `tests/` 覆盖 + 新增单测兜底；告警维持 try/except 非阻断，最坏只多打/少打日志，不影响落盘。
- 回滚：改进为纯增量，可 `git revert`；数据源未动，无回滚半径。
